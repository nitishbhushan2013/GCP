# Spec 002: Identity & Access Governance (Retrofit)

## Status

Draft → Implementing (manual review, via Console + gcloud)

## 1. Problem

Epic 2 (Identity & Access Governance) was never given its own spec. Its early
Stories (dedicated service account, scoped Secret Manager access, scoped Cloud SQL
role) were delivered opportunistically inside Epic 3's build (`specs/003-workload/`)
rather than planned and verified as their own unit of work. Two Stories remain
genuinely undone: Cloud Audit Logs have never been reviewed, and the project's full
IAM bindings have never been audited for over-broad grants. This spec closes that
gap and gives Epic 2 a proper, complete record.

## 2. Requirements

### 2.1 Cloud Audit Logs Review (PRD Story 2.4)

- Confirm Data Access audit logs are enabled for the services this project actually
  uses (at minimum: Cloud SQL, Secret Manager, IAM).
- Review actual log entries generated by real activity so far (e.g. the
  `budgetsense-run-sa` accessing secrets, connecting to Cloud SQL) and confirm they
  are being captured with enough detail to be useful (who, what, when).
- Document what's logged vs. not by default — Admin Activity logs are always on and
  free; Data Access logs (the ones that show _reads_ of secrets/data) are often
  off by default and may need explicit enabling per service.

### 2.2 Full IAM Bindings Review (PRD Story 2.5)

- List every IAM binding on the project — every principal, every role.
- For each binding, classify it as: (a) expected and correctly scoped, (b) expected
  but overly broad (should be tightened), or (c) unexpected (investigate — could be
  a default grant, a leftover from an abandoned experiment, or a mistake).
- Specifically check for: any principal with `Owner` or `Editor` beyond the account
  holder themselves, any service account with a broader role than it actually uses,
  and any binding left over from the reverted GKE exploration.
- Produce a findings table as part of the runbook — not just "looked fine," but the
  actual list with the classification per row.

### 2.3 Non-goals

- No new IAM roles or resources are being created in this spec — this is a review
  and documentation pass over what already exists.
- Organization Policies (data residency, public-IP restriction) are Epic 5, not
  this spec.
- If the review surfaces a genuine problem (an over-broad grant that should be
  fixed), the fix itself can happen as part of this spec's implementation — but the
  spec's primary deliverable is the _review_, with fixes as a natural consequence.

## 3. Acceptance Criteria

- [ ] Data Access audit logs confirmed enabled for Cloud SQL, Secret Manager, and IAM
      (or explicitly enabled as part of this spec if they weren't already).
- [ ] At least one real log entry for each of: a Secret Manager secret access by
      `budgetsense-run-sa`, and a Cloud SQL connection — found, reviewed, and
      understood (what fields it contains, what it proves).
- [ ] Full IAM policy binding list obtained (`gcloud projects get-iam-policy`) and
      every binding classified in the runbook.
- [ ] Any over-broad or unexpected binding found is either fixed or explicitly
      accepted with a documented reason (not silently left as "noted").
- [ ] `specs/002-identity/runbook.md` records the full findings table and any
      remediation taken.
- [ ] PRD Epic 2 Stories 2.4 and 2.5 updated from ⬜ to ✅ once complete.
